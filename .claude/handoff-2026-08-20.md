# Session Handoff — 2026-08-20

## Accomplished

Two macOS bugs from a real 15.6 session (reported in `voice-typer-bug.md`, untracked at
the repository root) were fixed, released, and documented.

- **The SIGTRAP crash at every paste** — `pynput.keyboard.Controller()` asks Carbon for the
  keyboard layout in its constructor, and on macOS 15 that call demands the main queue. The
  paste runs on a worker thread, so the process was killed outright. macOS now posts the
  four Cmd+V key events to Quartz itself. Shipped as v0.1.3 and **confirmed working on the
  user's Mac** — the app no longer dies.
- **The focus never coming back** — starting a take by clicking the record button moves the
  keyboard focus to this app, and nothing gave it back, so the paste went into our own
  canvas. New `voice_typer/focus.py`; macOS activates the remembered application through
  `NSRunningApplication.activateFromApplication:options:`. Shipped as v0.1.4, **not yet
  tested by the user**.
- **README** gained the two things the session exposed: F9 is taken by Mission Control on a
  Mac (three ways out), and replacing the `.app` silently invalidates the Accessibility
  grant — it has to be removed from the list with **−** and added again with **+**.

## Next Steps

1. **Wait for the user's macOS test of v0.1.4.** The check that matters: click into
   TextEdit, then start the take with the **mouse** on the record button, speak, stop. The
   Georgian sentence should land at the TextEdit caret. Then repeat with F9 to confirm the
   hotkey path still works.
   - If the message *"ტექსტი clipboard-შია — დააჭირე Cmd+V"* appears instead, macOS refused
     the activation. That is the designed fallback, not a crash — the next move is the
     `NSApp.yieldActivation(to:)` route through a Tk main-thread hop, written up as the
     first rejected alternative in ADR 005.
   - If the app crashes, ask for the first lines of the crash report and look for
     `logs/.focus_probe-frontmost` or `-activate` in
     `~/Library/Application Support/voice-typer/logs/`. Whichever file survives names the
     call that died.
2. **The real root cause is still open** — the Tk window should never take the focus in the
   first place. `window_platform._make_non_activating_macos` passes `help noActivates`, but
   `kHelpWindowClass` has a style mask of 0, so Tk builds an `NSWindow` rather than an
   `NSPanel` and the window server activates the app on click anyway. The attribute that
   works is `nonActivating`, and it must be applied **before** the window is realised —
   `overlay.py` applies the current one after `root.update()`, so it is probably already a
   no-op. Own commit, own verification; see the third rejected alternative in ADR 005.
3. **Ad-hoc signing drops the Accessibility grant on every rebuild.** Every update will look
   like the paste broke. A stable signing identity is the only real fix; the README
   workaround is the interim.

## Important Context

- The two macOS decisions and everything rejected along the way are in
  `docs/decisions/004-macos-paste-via-quartz.md` and `005-macos-focus-hand-back.md`. Read
  005 before touching `focus.py` — several obvious-looking simplifications are traps that
  end in silent word loss.
- `focus.py` uses only `NSWorkspace.frontmostApplication` and `NSRunningApplication`, both
  documented thread-safe. **`NSApplication` must never be called from a worker thread** —
  that is the same rule that caused the original crash.
- The token passed around as `target_window` is a window handle on Windows and a **process
  id** on macOS. Deliberate; `app.py` never learns the difference.
- `started_from_our_window` travels from `toggle_recording` down to `inject_text`. It exists
  for one case: when macOS cannot be asked where the focus is, the hotkey path may still
  paste and the button path may not.
- No Mac is available on this machine. Everything macOS-shaped is verified by the user on
  their own hardware, or not at all.
